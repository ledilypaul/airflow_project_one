# Veille techno — 2026-11-21 — Airflow 3.4

Périmètre : passer d'Airflow 3.3.2 (épinglé, `uv.lock`) à 3.4.0, sortie le 2026-11-06 sur PyPI. J'ai lu `pyproject.toml`, `uv.lock`, `CLAUDE.md`, `docs/audit/2026-11-05-baseline.md`, `Dockerfile`, `deploy/k8s/values-airflow.yaml`, `deploy/observability/rules/airflow.yml`, `utils/failure_alert.py`, `.github/dependabot.yml` et les DAGs. Je n'ai modifié aucun fichier.

Légende : **[vérifié]** = lu à la source officielle citée. **[supposé]** = déduit, non vérifié. **[non vérifié]** = information introuvable ou seulement chez des tiers.

## En bref

- **Pas de 3.3.3.** Le milestone GitHub « Airflow 3.3.3 » est fermé avec la mention « Won't be released. All items under this milestone are released in Airflow 3.4.0 ».
- **Au moins six CVE corrigées en 3.4.0 touchent 3.3.2**, publiées le 2026-11-09. L'une, CVE-2026-111453, ne touche que la plage 3.3.2 à 3.4.0, c'est-à-dire exactement notre version.
- **L'écosystème est prêt, sauf le chart Helm.** Cosmos 1.16.0, qui est déjà notre version, a ajouté 3.4 à sa matrice de test. Les providers utilisés sont tous à leur dernière version et n'imposent pas plus que `apache-airflow>=2.11`. Le chart Helm 1.23.0, celui qui vise 3.4.0, n'est pas sorti (milestone à 92 %).
- **Une rupture touche directement le projet** : les DAGs planifiés sur un Asset créent maintenant un run par événement, au lieu de regrouper les événements en un seul run.
- **Les images Docker 3.4 changent de base** : Docker Hardened Images, Debian 13. Notre `Dockerfile` fait un `apt-get install tini`, à revérifier.

## Q1 — Ce que 3.4.0 apporte d'utile ici [vérifié, [release notes](https://airflow.apache.org/docs/apache-airflow/stable/release_notes.html)]

**Assets**
- Un run par événement par défaut (#68517). On peut revenir au regroupement avec `batch_asset_events=True` sur le timetable, ou avec `[scheduler] batch_asset_events` (ajouté en 3.4.0, défaut `False`).
- Avec ce mode, `max_active_runs` est respecté : les événements en trop restent en file ([doc asset scheduling](https://airflow.apache.org/docs/apache-airflow/stable/authoring-and-scheduling/asset-scheduling.html)).
- Pour `read_file_dag`, c'est un gain : un listing donne un run, donc des retries isolés.
- Pour `transform_dag`, c'est un coût : un `dbt build` complet par événement `lake_staging`, là où un seul suffisait.

**Retries et cycle de vie des DAGs**
- Nouvel état `draining` : il bloque les nouveaux runs planifiés, laisse finir les runs actifs, puis met le DAG en pause. C'est utile avant un `helm upgrade`.
- Politiques de retry composables (`ChainRetryPolicy`, #73508) et retries qui replanifient sans consommer de tentative (#74993). C'est une piste pour remplacer un jour la logique « pas de retry sur 2/3/5/6 » de `ReadFilesSparkSubmitOperator`.

**Métriques et traces**
- Nouvelles métriques d'observabilité du scheduler (#68068). Leurs noms ne sont pas vérifiés.
- Les métriques de sérialisation sont renommées : `dag.serialization.version_created` / `version_updated` (#70838, [PR](https://github.com/apache/airflow/pull/70838)). Le projet ne les utilise pas.
- Correctifs `task.queued_duration` et `last_duration`.
- Les spans agents sont conservés quand le tracing worker est coupé, et l'échantillonnage des traces peut être forcé par run via la conf.

**UI**
- Action « Mark as Skipped ».
- Bascule des niveaux de log dans les logs de tâche.
- Filtre temporel dans le Gantt.
- Filtres d'événements d'Asset (extra, partition).

**Rien de notable** dans les notes pour le KubernetesExecutor (seule ligne : « Update supported Kubernetes versions », #73798), pour `[openlineage]` / `[lineage]` (une seule modification de doc, #71450) et pour `dag.test()`.

**À ignorer ici** : Task Loops (AIP-111), Dag Importer TypeScript/Go/Java/YAML (expérimental), provider `common.ai`, multi-team. Le [blog 3.4.0](https://airflow.apache.org/blog/airflow-3.4.0/) recommande lui-même d'épingler ce qui est expérimental.

## Q3 — Compatibilité de l'écosystème

**astronomer-cosmos**
- 1.16.0 est la dernière version ; il n'existe pas de 1.17 ([GitHub releases](https://github.com/astronomer/astronomer-cosmos/releases), [PyPI](https://pypi.org/pypi/astronomer-cosmos/json) : `apache-airflow>=2.11.0`, sans borne haute).

- 1.16.0a3 précise qu'en 3.4, vider (clear) le producteur watcher efface sa sauvegarde dans le task store, sauf si « Keep task state » est coché ([release](https://github.com/astronomer/astronomer-cosmos/releases/tag/astronomer-cosmos-v1.16.0a3)). Cela ne concerne que `enable_watcher_reliable_retry`, que le projet n'active pas.
- **Bug de câblage producteur/capteurs** (la raison pour laquelle `dag.test()` ne peut pas tester `transform_dag`) : je n'ai trouvé ni issue ni correctif qui le cite. **[non vérifié]**, donc à considérer comme toujours présent.

**Chart Helm**
- 1.22.0 est la dernière version publiée ; son image par défaut est 3.2.2.
- Sur `main`, `values.yaml` passe `defaultAirflowTag` et `airflowVersion` à `"3.4.0"`. La 1.23.0 est en cours (milestone : 5 issues ouvertes, 64 fermées).
- Que 1.22.0 fonctionne avec `airflowVersion: 3.4.0` est **[non vérifié]** (le projet l'a validé avec 3.3.2). Recommandation : attendre 1.23.0, ou tester 1.22.0 sur kind.

**Image** : `slim-3.4.0-python3.12` existe, voir la ligne d'impact Debian 13 / DHI plus haut.

**providers-apache-spark 6.3.4**
- Inchangé, et ne demande que `apache-airflow>=2.11.0`.
- Les attributs privés lus par le projet (`_submit_sp`, `_spark_exit_code`, `_is_kubernetes`, `_connection`) sont dans le hook du provider, pas dans le core. Une montée du core ne les touche pas, et aucun changelog 6.3.x ne les mentionne [vérifié pour le changelog]. Le test qui les épingle reste la seule garde.

**providers-cncf-kubernetes 11.0.0**
- Dernière version, sortie le 2026-11-09. Rupture : `cleanup_stuck_queued_tasks` est retiré, au profit de `revoke_task`. Le projet ne l'utilise pas [supposé].
- Que 11.0.0 implémente déjà les `executor_queues` / `supported_workload_types` de 3.4 est **[non vérifié]**. Les anciens attributs restent en shims qui émettent `RemovedInAirflow4Warning` : risque d'avertissement dans les logs, pas de casse.
- Le pin `<12` est correct.

**openlineage 2.21.0, postgres 7.1.2, standard 1.21.0** : ne demandent que `apache-airflow>=2.11.0`, aucune incompatibilité signalée. Monter postgres en 7.1.2 avec la migration.
