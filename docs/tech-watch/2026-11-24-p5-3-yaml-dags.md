# Veille techno — 2026-11-24 — Les DAGs en YAML d'Airflow 3.4 (P5-3)

Périmètre : la fiche P5-3 demande de ne pas s'appuyer sur le chargement de DAGs depuis du YAML
annoncé par Airflow 3.4 tant qu'il est expérimental, et de le noter dans la veille. Lu le
2026-11-24 dans la documentation d'Airflow 3.4.0. Aucun fichier du projet n'en dépend.

Légende : **[vérifié]** = lu à la source officielle citée. **[non vérifié]** = non essayé.

## En bref

- **C'est expérimental, et c'est dit en toutes lettres** [vérifié] : « This is an experimental
  feature », ajouté en 3.4.0
  ([Writing Dags in YAML](https://airflow.apache.org/docs/apache-airflow/3.4.0/authoring-and-scheduling/yaml-dags.html)).
  Les notes de version ajoutent que le cadre des *Dag Importers* est expérimental et que son API
  peut changer
  ([release notes 3.4.0](https://airflow.apache.org/docs/apache-airflow/3.4.0/release_notes.html)).
- **Il n'est pas actif par défaut** [vérifié] : l'importeur se déclare dans `[dag_processor]
  dag_importer_configs` (classe `airflow.sdk.importers.yaml_importer.YamlDagImporter`), sur chaque
  composant qui charge des DAGs
  ([Dag Importers](https://airflow.apache.org/docs/apache-airflow/3.4.0/administration-and-deployment/dag-importers.html)).
  Il ne lit que les fichiers qui portent le marqueur `$schema` : nos YAML de sources, qui n'en ont
  pas et vivent hors du dossier des DAGs, ne sont jamais pris pour des DAGs.
- **Il ne couvre pas ce dont la fabrique a besoin** [vérifié, même page] : pas d'`inlets` ni
  d'`outlets` (les Assets sont refusés, le planning par Asset n'est pas disponible), pas de
  `.expand()`, pas de groupes de tâches, et les arguments qui doivent être des objets Python
  (callbacks) ne passent pas. Or `ingest__<source>` émet un Asset et `transform_dag` est planifié sur
  leur union ; tous deux utilisent les callbacks d'échec (P3-3) et un opérateur à nous.

## Décision

P5-3 génère les DAGs **en Python** (`dags/source_pipelines.py`), comme le projet le fait déjà, à
partir de **nos** YAML de sources (validés par Pydantic, un seul modèle). À revoir quand la fonction
sera stable **et** qu'elle acceptera les Assets et les callbacks. Même alors, il faudrait un
générateur de ces YAML-là depuis ceux des sources : pas de gain tant que le Python tient en
quelques centaines de lignes.

## À étudier plus tard (hors périmètre de P5-3)

- **`AssetWatcher`** (déclencheurs d'Assets événementiels) pour un planning « à l'arrivée du
  fichier » plutôt qu'un cron : [non vérifié], à étudier. Le planning d'une source reste un cron,
  un preset ou le lancement manuel.
- **`AssetAny`** [vérifié, sur l'Airflow installé] : exporté par `airflow.sdk`, accepté par
  `AssetTriggeredTimetable(AssetAny(*assets), batch_asset_events=True)` ; l'union de deux Assets
  avec le regroupement donne bien **un** run qui consomme les événements des deux sources
  (`tests/integration/test_p3_5_asset_scheduling.py`). La page de planification des Assets n'écrit
  que l'opérateur `|` ; `AssetAny` en est la forme objet et se compare par égalité dans les tests
  ([Asset scheduling](https://airflow.apache.org/docs/apache-airflow/stable/authoring-and-scheduling/asset-scheduling.html)).
