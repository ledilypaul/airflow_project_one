- La 3.3 ne recevra plus de correctif : le milestone 3.3.3 est fermé (« Won't be released »).

## 3. Le changement de comportement : un run par événement d'Asset

En 3.4.0 (#68517), un DAG planifié sur un Asset crée **un run par événement**. La 3.3 regroupait tous les événements en file dans un seul run. Le défaut vient de `[scheduler] batch_asset_events` (`False`) et est lu quand le timetable est construit : il dépend donc du déploiement.

Les deux DAGs fixent désormais la valeur eux-mêmes, avec `schedule=AssetTriggeredTimetable(<asset>, batch_asset_events=...)` (`from airflow.sdk import AssetTriggeredTimetable`, vérifié dans le Task SDK 1.4.0 installé) :

| DAG | `batch_asset_events` | Effet |
|---|---|---|
| `read_file_dag` | `False` | Un run par listing, donc une application Spark par run source, avec ses propres retries et son propre état. Avec `max_active_runs=1`, les autres événements restent en file (lignes `AssetDagRunQueue`) et donnent chacun leur run, l'un après l'autre. Aucun n'est perdu. |
| `transform_dag` | `True` | Les événements `lake_staging` arrivés pendant un `dbt build` sont consommés ensemble par **un seul** run suivant. Chaque run reconstruit toute la zone staging, donc un build par événement referait le même travail. |

- **`resolve_source_run_ids`** reste correct dans les deux cas. Il dédupliquait déjà la liste des événements ; il en reçoit maintenant un seul par run. La boucle sert encore si le regroupement est réactivé.
- **La condition** est maintenant l'Asset lui-même, et non plus `AssetAll([asset])` comme avec `schedule=[asset]`. Un `AssetAll` d'un seul Asset n'imposait pas de regroupement : le défaut était donc bien `False` pour les deux DAGs.
- **Montée de version** : un DAG sérialisé par 3.3 n'a pas la clé, et 3.4 le relit avec `batch_asset_events=True` (`data.get("batch_asset_events", True)`) jusqu'à sa re-sérialisation. Les deux fichiers de DAG changent : le DAG processor les re-sérialise au premier parsing.

### Événement émis pendant une pause (point non vérifié de la veille)

**Vérifié dans le code installé, et par un test.**

- `AssetManager.register_asset_change` ne crée de ligne `AssetDagRunQueue` que pour les DAGs ni en pause ni en `draining`. C'était déjà le cas en 3.3.
- En 3.3, le run suivant prenait tous les événements depuis le run précédent, sur une fenêtre de temps : l'événement émis pendant la pause était donc consommé.
- En 3.4, avec `catchup=False`, le scheduler ne consomme que les événements en file (`_select_consumed_asset_events`). **Un événement émis pendant la pause n'est donc plus jamais consommé.**

Conséquence, documentée dans CLAUDE.md :
- `read_file_dag` : les fichiers de ce listing restent `pending`. Il faut déclencher le DAG à la main avec `{"run_id": "<dag_run_id du listing>"}`, ou relancer un listing, qui reliste les fichiers.
- `transform_dag` : sans conséquence, le prochain événement reconstruit tout.
- Passer `catchup=True` n'est **pas** la bonne réponse : avec un `start_date` de 2023, le scheduler rejouerait tout l'historique des événements, un run par événement. Ce point est laissé hors périmètre.

`tests/integration/test_p3_5_asset_scheduling.py` vérifie les trois comportements sur le **scheduler** réel de la version installée : vrais fichiers de DAG synchronisés dans une base SQLite migrée, vrais événements, appel de `SchedulerJobRunner._create_dagruns_for_dags`. Il passe une fois avec chaque défaut de `[scheduler] batch_asset_events`. Il échoue si l'on inverse le drapeau de `read_file_dag` ou si l'on retire celui de `transform_dag` : les deux mutations ont été essayées.

## 5. Image Kubernetes : conflit image / lock

L'image fait `uv sync --frozen` sur `uv.lock` et remplace les paquets de l'image de base par ceux du lock. Avec le lock en 3.4.0 et une base en 3.3.2, l'image aurait fait tourner Airflow 3.4.0 avec l'entrypoint, la variable `AIRFLOW_VERSION` et le système de la 3.3.2. Ce mélange n'a jamais été testé.

Trois options étaient possibles :
1. garder la base 3.3.2 : mélange incohérent, sans erreur visible ;
2. donner à l'image un lock à part en 3.3.2 : deux locks racine à suivre (Dependabot, `pip-audit`), et l'image ne profite pas des correctifs CVE ;
3. **passer la base à `apache/airflow:slim-3.4.0-python3.12@sha256:2d3e42b9de0eca948b9a869817068fedcb8a8eac9827b1e6215de3329d59335f`. C'est le choix retenu.**

Le digest d'index a été relu avec `docker buildx imagetools inspect` le 2026-11-21. Le test `test_p3_2_airflow_base_is_the_version_of_the_lock` impose désormais que le tag de la base porte la version d'Airflow du lock.

Vérifié dans cette image (base DHI, Debian 13) :
- `root` est disponible ;
- `apt-get`, `curl`, `sha256sum` et `install` sont présents ;
- `apt-get install tini` fonctionne (tini 0.19.0) ;
- `uv` est sous `/home/airflow/.local/bin/uv` et Python 3.12.16 sous `/usr/python/bin/python3.12`, les chemins utilisés par le `Dockerfile` ;
- glibc est en 2.41.

`make image IMAGE_TAG=p3-5-smoke` réussit sans autre changement du `Dockerfile`. Dans l'image produite :
- `airflow version` répond 3.4.0 ;
- le JRE Temurin 17.0.21 « noble » tourne sur Debian 13 ;
- `/usr/bin/tini` est présent ;
- `spark-submit --version` répond 4.3.0 ;
- `cosmos` et le provider postgres s'importent ;
- l'utilisateur est 50000.

**Limites, laissées à P3-6 :**
- Le chart officiel 1.22.0, `airflowVersion: "3.3.2"` dans `deploy/k8s/values-airflow.yaml` et `appVersion` du chart du projet ne changent pas. Les gabarits du chart 1.22.0 ne comparent `airflowVersion` qu'à 2.11.0 et 3.0.0 (vérifié dans l'archive), donc 3.3.2 et 3.4.0 produisent les mêmes manifestes. Le chart n'est pas pour autant validé avec 3.4.
- Aucun cluster kind n'a été lancé. Restent à revalider : les pods driver et exécuteur (entrypoint Spark vendoré), le passage de l'URL `postgresql://` en psycopg3 et le pool de connexions async de l'API server.
- Le déploiement Kubernetes n'est donc **pas revalidé** en 3.4 : à faire dans P3-6 avant tout `make k8s-install` sur une nouvelle image.

## 6. `filterwarnings`

Inchangé : la suite complète passe sur 3.4.0 avec `RemovedInAirflow4Warning`, `AirflowProviderDeprecationWarning` et `DeprecatedImportWarning` transformés en erreurs. Seule exception, conservée : le `DeprecatedImportWarning` levé depuis `cosmos`. Cosmos 1.16.0 n'a été testé que sur une bêta 3.4 : son bug de câblage producteur/capteurs est considéré comme toujours présent (aucun correctif publié), et `transform_dag` reste hors de `dag.test()`.

## 7. Dependabot

La règle `apache-airflow` reste « correctifs seulement », mais sur la 3.4 : elle propose 3.4.1 et pas 3.5. Le commentaire est mis à jour. Une nouvelle mineure se prépare à la main : providers, Cosmos, Task SDK, image, chart, sémantique des Assets.
