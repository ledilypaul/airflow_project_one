## 🔴 Critique

### S1 — Mot de passe admin commité dans un dépôt public 🔍
`simple_auth_manager_passwords.json.generated` est versionné et le repo est **public**. Il contient le mot de passe de l'utilisateur `admin` du Simple Auth Manager.
- **Impact :** quiconque lit le repo peut se connecter en admin à toute instance qui réutilise ce fichier.
- **Correctif :**
  1. Supprimer le fichier en local (Airflow en régénère un nouveau au démarrage) → nouveau mot de passe.
  2. `git rm --cached simple_auth_manager_passwords.json.generated` + l'ajouter au `.gitignore`.
  3. Le fichier reste dans l'historique Git : considérer l'ancien mot de passe comme compromis (étape 1 suffit), et purger l'historique avec `git filter-repo` si tu veux un historique propre.

### B1 — Tout fichier sans config dédiée plante (`KeyError: 'source'`) ✅
`BaseFileReader.read_file()` lit `file_config["source"]["format"]`, mais le fallback `basic_reading_config.yaml` n'a pas de clé `source` (il a `format` à plat). Reproduit sur `random_data.csv` → `KeyError: 'source'`. C'est aussi le test qui échoue : `tests/unit/file_reader/test_base_reader.py::test_read_file`.
- **Correctif :** unifier les deux formes de config (voir M4). À court terme : `fmt = file_config.get("source", {}).get("format") or file_config.get("format")`.

### B2 — Tous les fichiers IMDB plantent (type `array` inconnu) ✅
`config/imdb_config.yaml` déclare `genre_list: array`, absent de `get_spark_type()`. Reproduit → `ValueError: Type non reconnu dans YAML : 'array'`.
- **Correctif :** ajouter `"array": ArrayType(StringType())` (ou une syntaxe `array<string>`), et un test par config YAML existante qui construit son schéma.

### B3 — Tous les fichiers Excel plantent dans le job Spark ✅
`ExcelReader.read()` renvoie un **pandas-on-Spark** DataFrame, qui n'a pas de méthode `.show()` (vérifié). Or `read_files_job.py` appelle `content.show(...)`. De plus `openpyxl` (requis par `read_excel`) n'est déclaré nulle part, et `spark-excel` n'est chargé qu'en `ENV=prod`.
- **Correctif :** renvoyer un DataFrame Spark (`ps.read_excel(...).to_spark()`), déclarer `openpyxl`, et typer le contrat des readers (`-> pyspark.sql.DataFrame`) via une classe abstraite.

## 🟠 Élevé

### S2 — `airflow.cfg` versionné 🔍
Contient les chemins absolus de ta machine et une `secret_key` générée (commentée). Il n'a pas à être dans Git.
- **Correctif :** retirer du suivi, configurer via variables `AIRFLOW__SECTION__CLE` (ou `.env` non versionné) ; documenter la config minimale dans le README.

### S3 — `docker-compose.yaml` : identifiants par défaut et Redis exposé 🔍
Postgres `airflow/airflow` exposé sur `5433`, Redis exposé sur `6379` **sans mot de passe**, clé `version:` obsolète. Le compose ne contient **aucun service Airflow**, alors que le CLAUDE.md documente `docker compose run airflow-webserver airflow db init` (et `db init` / `webserver` n'existent plus en Airflow 3 : c'est `db migrate` / `api-server`).
- **Correctif :** partir du `docker-compose.yaml` officiel Airflow 3.3, secrets via `.env`, ne publier que les ports nécessaires (bind sur `127.0.0.1`).

### S4 — `setup_airflow.sh` : admin en dur et commande morte 🔍
Crée `pol/pol` en Admin. La commande `airflow users create` n'existe pas avec le Simple Auth Manager, et ne s'exécuterait de toute façon jamais (`airflow standalone` est bloquant).
- **Correctif :** supprimer le script ou le réécrire sans identifiants.

### S5 — `.gitignore` minimal 🔍
Ne couvre ni `.env`, ni `airflow.db`, ni `logs/`, ni `airflow.cfg`, ni `data/`, ni les sorties de notebooks.

### D1 — Dépendances incohérentes et Airflow 2 en fin de vie 🔍✅
- `pyproject.toml` ne déclare que `pyspark`, `pyyaml`, `pytest` (pytest en dépendance de prod). Manquent : Airflow, SQLAlchemy, psycopg2, python-dotenv, pandas, openpyxl, polars.
- `requirements.txt` est encodé en **UTF-16** (casse beaucoup d'outils), épingle **Airflow 2.10.4** (Airflow 2 est en fin de vie depuis avril 2026), PySpark 3.5.4, SQLAlchemy 1.4, et embarque `crewai`, `chromadb`, `langchain`, `openai` sans rapport avec le projet (surface d'attaque et conflits). Le CLAUDE.md le dit « in sync » : ce n'est pas le cas.
- `pandas` non borné : **pandas 3 casse l'import de `pyspark.pandas`** avec PySpark 4.0.5 et encore avec 4.3.0, la dernière version (vérifié : `ImportError: cannot import name 'DateOffset'`).
- **Correctif :** migrer vers **uv** — `pyproject.toml` PEP 621 fourni dans le kit (groupes `airflow` et `dev`, `pandas<3`, Airflow 3.3.2), `uv.lock` commité, suppression de `poetry.lock` ; `requirements.txt` supprimé ou généré par `uv export` en UTF-8. Validé le 2026-11-07 sur une copie du repo : 164 paquets résolus en 4 s, mêmes résultats de tests qu'avant (63 passés, 1 échec B1 ; tests de DAG en échec T1 inchangés). Les constraints Airflow 3.3.2 complètes ne sont pas applicables telles quelles (elles imposent pandas 3.0.5) : le lockfile assure la reproductibilité, et on compare les versions Airflow/providers aux constraints en revue.

### T1 — Les tests de DAG ne passent pas sous Airflow 3.3 ✅
Trois causes indépendantes dans `tests/unit/dags/test_dags.py` :
1. `DagBag(..., include_examples=False)` → `TypeError` (argument retiré ; utiliser `AIRFLOW__CORE__LOAD_EXAMPLES=False`).
2. Les task_ids attendus pour `list_files_dag` sont ceux de la version classique (`list_files_task`, `insert_files_to_db`) ; la version TaskFlow a `list_files` et `insert_files`.
3. `dag.schedule_interval` n'existe plus → utiliser `dag.schedule` / `dag.timetable`.

### A1 — Pipeline non idempotent et non traçable 🔍
- Le job Spark sélectionne `ingested_at = CURRENT_DATE` au lieu des fichiers **du run** (`dag_run_id`) : un listing à 23h59 lu à 00h01 est perdu, un rerun retraite tout.
- Le statut reste `pending` à vie (jamais `processed` / `failed`).
- Le job sort en code 0 dès qu'**un** fichier réussit : les échecs partiels sont silencieux.
- Rien n'est écrit : le job fait `.show()` et s'arrête (les writers existent mais ne sont pas branchés).
- L'index `idx_file_path` n'est pas `UNIQUE` (le commentaire SQL dit « unicité ») → doublons à chaque rerun.

## 🟡 Moyen

### M1 — Imports dépréciés en Airflow 3 ✅
8 avertissements au chargement : `airflow.decorators.dag/task` → `airflow.sdk`, `airflow.operators.bash/python` → `airflow.providers.standard.operators.*`, `get_current_context` → `airflow.sdk`.

### M2 — Répertoire vide = DAG en échec 🔍
`insert_files` lève `ValueError` si aucun fichier : un run « rien à faire » apparaît rouge. Préférer `AirflowSkipException` ou un short-circuit.

### M3 — Connexions base de données 🔍
Un `create_engine()` par ligne insérée (aucun pool réutilisé) ; identifiants lus depuis `.env` plutôt qu'une **Connection Airflow** (`PostgresHook`, secrets backend) — impossible à faire tourner proprement en multi-environnement.

### M4 — Résolution de config fragile 🔍
- Choix de la config par sous-chaîne du préfixe de nom de fichier, dans l'ordre non déterministe de `os.listdir` : `extractor_config.yaml` capterait tout fichier contenant « extractor ».
- Deux formes de YAML coexistent (`reader.reader_options` vs `reader_options`) et les readers ne lisent pas la même.
- `CSVReader` ignore `encoding` ; la section `txt` utilise `infer_schema` au lieu de `inferSchema`.
- **Cible :** un mapping explicite (`patterns:` → config), un schéma de config validé (Pydantic), une seule forme.

### M5 — Packaging par `sys.path` 🔍
Chaque DAG/job modifie `sys.path`. `sandbox` est packagé dans `pyproject.toml`. Cible : paquet installé en éditable par `uv sync` (vérifié : `import pipeline.*` fonctionne sans `PYTHONPATH`), puis suppression des manipulations de `sys.path`.

### M6 — Orchestration Spark via `BashOperator` 🔍
Pas de config de ressources, pas de pool, logs Spark mêlés au stdout. Cible : `SparkSubmitOperator` (provider `apache.spark`) puis Spark on Kubernetes.
